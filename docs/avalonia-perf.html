Avalonia performance parity

Numbers come from --perf-bench <out.json> (CCP.Avalonia/PerfBench.cs, ConditioningControlPanel/PerfBench.cs), run on the real windowing platform, never headless. Decision and threshold: docs/avalonia-decisions.html (2026-10-23). A row passes when the Avalonia median is ≤ WPF median × 1.10 + 20 ms (memory: ≤ WPF × 1.10), both heads measured back to back on the same windows-latest runner. Linux is information only. A row with no WPF number is a gap, not a pass.

What is measured

  • Startup: a Stopwatch started on the first line of Main, stopped when the render thread has drawn the first frame after the shell's Opened. The shell is built straight after SetupWithoutStarting: no splash, no account/session seeding, no launcher routing. WPF starts the clock on the first line of its custom Main, runs its normal service startup, then shows the real main window directly, timed with CompositionTarget.Rendering and sampled after that Render-priority pass returns. Splash, launcher routing and modal onboarding are bypassed only under the flag; the WPF startup ladder is held and the sandbox is an onboarded offline user. startup_since_process_ms adds the runtime's own start-up (process start time to the same frame). Startup is informational, not a gate: the scopes differ (WPF includes its full service init, Avalonia does not), so perf-compare.py reports both startup rows as info and never fails on them.
  • Tab switch: ShowTab (the call every rail handler makes) to the next rendered frame, for every panel in NavCheck.TabPanels, 21 cycles with the first discarded; median (middle pair averaged) and p95 (nearest rank) per tab. Frame done differs slightly: Avalonia waits for RequestCompositionBatchCommitAsync().Rendered (render thread included), WPF stops at a Background hop after CompositionTarget.Rendering (UI thread committed, before the render thread presents), so tab rows lean slightly against Avalonia; the 20 ms slack is meant to absorb it.
  • Idle Home (Avalonia only, informational): idle_home_frame_requests_per_s, the frames the window's FrameClocks requested per second over 3 s on Home after a 1 s settle. A clock parks between beats on a one-shot timer and a clock whose owner is detached, hidden or minimised requests nothing, so this sits near the beat rate (30/s), not the monitor refresh.
  • Memory: working set after the cycles and two GC.Collect + WaitForPendingFinalizers passes.
  • Exit 0 with the JSON written; 3 when a tab is missing or does not show; 4 on a frame timeout (30 s). WPF also exits 2 with usage on a bad command line or a non-absolute CCP_USERDATA_DIR, and every WPF benchmark exit goes through PerfBench.Exit (flush, then TerminateProcess), because Environment.Exit crashes WPF in ProcessExit and loses the code.

JSON shape ccp-perf-bench/1 (the WPF twin writes the same shape, head: "wpf"):

{ "schema": "ccp-perf-bench/1", "head": "avalonia", "os": "...", "runtime": "...",
  "startup_ms": 0, "startup_since_process_ms": 0, "working_set_mb": 0, "cycles": 20,
  "idle_home_frame_requests_per_s": 0,
  "tabs": [ { "tab": "SettingsTab", "median_ms": 0, "p95_ms": 0 } ] }

CI: perf-bench-linux (xvfb, artifact perf-bench-linux) and perf-bench-windows (artifact perf-bench-windows) in .github/workflows/build.yml. Windows publishes both heads as they ship (Avalonia win-x64 profile, WPF ReadyToRun single-file), runs five Avalonia/WPF pairs sequentially on the same runner with a fresh CCP_USERDATA_DIR per process (four-minute outer timeout each), and checks that a WPF run with a missing tab exits 3 without JSON. The job is report-only until three consecutive stable runs have been reviewed.

Compare reports (Python stdlib only): python3 .github/scripts/perf-compare.py --self-test, then python3 .github/scripts/perf-compare.py --avalonia 'perf-results/avalonia-*.json' --wpf 'perf-results/wpf-*.json'. It takes each metric's median across runs (per-tab median and p95 too), applies the rule above, prints a Markdown table and exits 1 on a regression, missing reports, missing/extra tabs or invalid measurements. Tab keys are NavCheck.TabPanels; WPF's legacy ExclusivesTab goes through ShowTab("exclusives") to the lazy Premium page, whose visibility is checked.

Render path on a GPU-less Windows machine

When every DXGI adapter is the Microsoft Basic Render Driver (WARP: vendor 0x1414 device 0x8C, or DXGI_ADAPTER_FLAG_SOFTWARE) and CCP_WIN32_RENDERING is unset, the Windows head renders with Skia software instead of ANGLE on WARP (Program.Win32Options, Platform/RenderBudget.ChooseRendering, Platform/DxgiAdapters.cs). The log line Win32 rendering: ... names the choice and the adapters. A machine with any real GPU keeps Avalonia's default. The view rebuilt its three lists three times per switch (visibility hook, RefreshEntitlementVeils, the posted LobbyPoll.Changed) and once on every other tab switch; it now rebuilds nothing when the data is unchanged. Every slow sample is Avalonia's UiThreadRender job, a whole-window software draw (about 50-65 ms, the same on RemoteControl, Subjects and Bambi, and unchanged when the Subjects fog, backgrounds or lobby columns are hidden) landing in the switch. The view's own work is under 0.1 ms, so the remaining tail is frame phase and shell-wide draw cost. The p95 shift sits at the 5% edge and is not a Windows result.
